# 运行事件与 ToolResult 设计记录

> 文档性质：部分已实施、部分提案。当前架构事实以 [ARCHITECTURE.md](ARCHITECTURE.md) 为准。

## 已实施：运行事件账本

`app/core/runtime_events.py` 已实现追加式运行事件，用于关联每日研究批次、步骤和外部工具调用。

### 数据模型

| 表 | 当前用途 |
|---|---|
| `runtime_run` | 保存根任务、合同版本/哈希、规范化输入哈希和状态 |
| `runtime_step_run` | 保存步骤、顺序、尝试次数、结果哈希和错误类型 |
| `runtime_event` | 保存根任务内连续序号、事件类型、状态和清理后的载荷 |

当前特性：

- 根任务内使用连续 `seq`，事件只追加不覆盖；
- 通过 `RunContext` 和 `ContextVar` 关联步骤与 iFinD/LLM 调用；
- 对密码、Token、API Key、Authorization 等字段做递归清理；
- 事件载荷限制为 64 KiB，超限只保存原始哈希和键摘要；
- 服务重启后，将运行中的每日批次和事件任务标记为失败，允许重新运行；
- 已完成批次步骤可复用，并记录 `step_reused`。

领域表仍是业务数据的权威记录：Evidence、策略版本、订单、成交和持仓不能由事件载荷恢复或修改。事件账本只负责关联和审计。

## 未实施：通用 ToolResult

以下内容仍是设计方向，不是当前能力：

- 独立 `tool_result` 权威表；
- 所有工具统一的输入/输出 Schema 注册表；
- 通用 `ToolExecutor`；
- 由声明式 `TaskSpec` 替代每日批次 Python handler；
- SSE 增量事件推送和通用事件 Reducer；
- Agent/Swarm 自动根据 ToolResult 修改研究流程。

当前外部调用仍由各领域适配器返回普通 Python 对象，并由各自重试、超时和熔断逻辑负责。不能再叠加一层通用重试，否则可能重复调用收费接口或重复写入。

## 后续实现约束

若继续建设 ToolResult，应保持：

1. 工具结果只能生成候选产物，不能直接批准订单、修改仓位或覆盖 Evidence。
2. 业务数据写入仍由领域服务执行，通用执行器不跨越数据库所有权。
3. 工具版本、输入哈希、输出哈希和错误分类必须可追溯。
4. 重试只有一个所有者；认证、权限和合同错误不可重试。
5. 先为少量只读工具验证合同，再考虑迁移每日批次。

在上述组件落地前，代码和运维文档不得把它们描述为已上线能力。
